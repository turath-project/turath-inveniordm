# Developer Guide: Integrating HOCR Annotation & Search Services

## 1. Goal

The primary objective of this work was to integrate two external Python Flask-based services into the main InvenioRDM Docker Compose environment:

1.  **Annotation Service:** Generates IIIF annotations (word boundaries) based on HOCR files for a specific book page.
2.  **Search Service:** Provides a IIIF Content Search API endpoint, allowing text search within the HOCR files of a book.

The goal was to make these services part of the standard `docker compose up` workflow, ensuring they could access necessary HOCR data and that the IIIF manifests generated by the `upload_book.py` script linked to these containerized services correctly.

## 2. Initial State

Before this integration, the system relied on:

*   **InvenioRDM:** Running via Docker Compose, managing records and serving files (PDFs, HOCR).
*   **Cantaloupe IIIF Image Server:** Running via Docker Compose, serving page images from PDFs.
*   **Annotation & Search Services:** Running as **separate, external** Python processes (e.g., `python app.py` on the host machine or another server).
*   **HOCR Data Access:** These external services were configured to read HOCR files directly from a **local filesystem path** (e.g., `./books/<book_id>/hocr/`), requiring HOCR data to exist both within the InvenioRDM record *and* on the local filesystem where the services ran.
*   **Manifest Linking:** The `upload_book.py` script generated IIIF manifests pointing to these external services using `http://localhost:5001` (search) and `http://localhost:5002` (annotations).

This setup was functional for local development but not robust or easily deployable.

## 3. The Plan

The integration plan involved the following steps:

1.  **Containerize Services:** Create Dockerfiles for the annotation and search Flask applications.
2.  **Integrate into Docker Compose:** Add service definitions for the annotation and search services to the project's `docker-compose.yml`.
3.  **Handle HOCR Data Access:** Devise a method for the containerized services to access the necessary HOCR files for the relevant books. The chosen initial approach was to use a **shared Docker bind mount** from the host.
4.  **Refactor Service Code:** Remove hardcoded paths and URLs from the Flask applications, making them configurable via environment variables.
5.  **Update Manifest Generation:** Modify `scripts/upload_book.py` to:
    *   Generate IIIF manifest URLs pointing to the containerized services (using Docker service names or proxied public URLs).
    *   Implement logic to copy HOCR files to the shared host directory (bind mount source) after successful upload to InvenioRDM.

## 4. Implementation Steps (How-To)

### 4.1. Creating Service Code Structure

*   Created a `services/` directory in the project root.
*   Created subdirectories for each service: `services/annotation_service/` and `services/search_service/`.
*   Placed the respective Flask application code into `app.py` files within these directories.

```bash
mkdir -p services/annotation_service
mkdir -p services/search_service
# (Copy/paste Flask code into services/annotation_service/app.py and services/search_service/app.py)
```

### 4.2. Refactoring Service Code

The original Flask `app.py` files contained hardcoded paths and URLs (e.g., reading HOCR from `os.getcwd()`, using `localhost:5001`/`localhost:5002`). This needed to be changed for containerization.

*   **HOCR Path:** Modified the code to read HOCR files from a fixed base path within the container, configured via an environment variable (`HOCR_BASE_DIR`), defaulting to `/hocr_data/books`.

    *Example Change (Conceptual):*
    ```python
    # Before:
    # hocr_dir = os.path.join(os.getcwd(), 'books', book_id, 'hocr')

    # After:
    HOCR_BASE_DIR = os.environ.get('HOCR_BASE_DIR', '/hocr_data/books')
    book_hocr_dir = os.path.join(HOCR_BASE_DIR, book_id, 'hocr')
    ```
*   **Service URLs:** Modified the code to construct internal and external URLs using base URLs provided by environment variables (e.g., `ANNOTATION_SERVICE_BASE_URL`, `SEARCH_SERVICE_BASE_URL`, `IIIF_SERVER_BASE_URL`).

    *Example Change (Conceptual):*
    ```python
    # Before:
    # annotation_list_id = f"http://localhost:5002/annotations/{book_id}/{page_identifier}/line"

    # After:
    ANNOTATION_SERVICE_BASE_URL = os.environ.get('ANNOTATION_SERVICE_BASE_URL', 'http://localhost:5002')
    annotation_list_id = f"{ANNOTATION_SERVICE_BASE_URL}/annotations/{book_id}/{page_identifier}/line"
    ```
*   **Configuration:** Added logging and made ports, SSL settings, and CORS origins configurable via environment variables.

### 4.3. Creating Dockerfiles

Created a `Dockerfile` in each service directory (`services/annotation_service/Dockerfile` and `services/search_service/Dockerfile`).

*Example Dockerfile (`services/annotation_service/Dockerfile`):*
```dockerfile
# Use an official Python runtime as a parent image
FROM python:3.9-slim

# Set the working directory in the container
WORKDIR /app

# Copy the requirements file into the container at /app
COPY requirements.txt .

# Install any needed packages specified in requirements.txt
RUN pip install --no-cache-dir -r requirements.txt

# Copy the current directory contents into the container at /app
COPY . .

# Make port 5002 available
EXPOSE 5002

# Define environment variable defaults
ENV PORT=5002
ENV FLASK_APP=app.py
ENV FLASK_RUN_HOST=0.0.0.0
ENV HOCR_BASE_DIR=/hocr_data/books
ENV ANNOTATION_SERVICE_BASE_URL=http://annotation-service:5002
ENV IIIF_SERVER_BASE_URL=http://nginx:80
ENV USE_SSL=false

# Run app.py when the container launches, listening on the specified PORT (Shell form for variable substitution)
CMD flask run --host=0.0.0.0 --port=$PORT
```

*   **Key Parts:**
    *   `FROM python:3.9-slim`: Uses a lightweight Python base image.
    *   `WORKDIR /app`: Sets the working directory inside the container.
    *   `COPY requirements.txt .`: Copies the dependency file.
    *   `RUN pip install ...`: Installs Python packages.
    *   `COPY . .`: Copies the service's Python code (`app.py`) into the container.
    *   `EXPOSE 5002`: Informs Docker that the container listens on this port.
    *   `ENV ...`: Sets default environment variables. Crucially, `ANNOTATION_SERVICE_BASE_URL` and `SEARCH_SERVICE_BASE_URL` use the Docker service names (`annotation-service`, `search-service`) for internal communication. `IIIF_SERVER_BASE_URL` assumes `nginx` is the proxy.
    *   `CMD flask run ...`: Specifies the command to run when the container starts, using the shell form (`flask run ... --port=$PORT`) to allow the `$PORT` environment variable to be correctly substituted.

### 4.5. Updating `docker-compose.yml`

Added the new services to the main `docker-compose.yml` file.

*Example Snippet:*
```yaml
services:
  # ... other services (cache, db, etc.) ...

  # Turath Annotation Service (HOCR-based)
  annotation-service:
    build:
      context: ./services/annotation_service # Build from the Dockerfile in this dir
    restart: "unless-stopped"
    ports:
      # Map container port 5002 to host port 5002 (accessible only locally)
      - "127.0.0.1:5002:5002"
    volumes:
      # Mount the host directory to the data path inside the container
      # NOTE: Assumes ./hocr_mount exists on the host!
      - ./hocr_mount:/hocr_data
    environment:
      - FLASK_DEBUG=1 # Enable debug mode for development
      - PORT=5002
      - HOCR_BASE_DIR=/hocr_data/books # Matches path in app.py
      - ANNOTATION_SERVICE_BASE_URL=http://annotation-service:5002 # Internal URL
      - IIIF_SERVER_BASE_URL=http://nginx:80 # Assumes nginx proxy
      - USE_SSL=false
      # Define allowed origins for CORS (adjust as needed)
      - CORS_ALLOWED_ORIGINS=http://localhost:3000,http://127.0.0.1:3000,http://localhost:8000,http://127.0.0.1:5000
    expose:
      - 5002 # Expose port internally

  # Turath Search Service (HOCR-based)
  search-service:
    build:
      context: ./services/search_service
    restart: "unless-stopped"
    ports:
      - "127.0.0.1:5001:5001" # Map internal 5001 to host 5001
    volumes:
      # Mount the same host directory
      - ./hocr_mount:/hocr_data
    environment:
      - FLASK_DEBUG=1
      - PORT=5001
      - HOCR_BASE_DIR=/hocr_data/books
      - SEARCH_SERVICE_BASE_URL=http://search-service:5001 # Internal URL
      - IIIF_SERVER_BASE_URL=http://nginx:80
      - USE_SSL=false
      - CORS_ALLOWED_ORIGINS=http://localhost:3000,http://127.0.0.1:3000,http://localhost:8000,http://127.0.0.1:5000
    expose:
      - 5001

# NOTE: The named volume 'hocr-data' was removed as we switched to a host bind mount
# volumes:
#   data:
#   images:
#   image_tiles:
#   # hocr-data: {} # Replaced by bind mount from host directory
```

*   **Key Parts:**
    *   `build: context: ...`: Tells Compose to build the image using the Dockerfile in the specified directory.
    *   `ports: - "127.0.0.1:5001:5001"`: Maps the container's port (right side) to a port on the host machine (left side), but only accessible via `127.0.0.1` on the host.
    *   `volumes: - ./hocr_mount:/hocr_data`: This is the **bind mount**. It maps the `./hocr_mount` directory from the host machine (where the `docker compose` command is run) to the `/hocr_data` directory inside the container. This allows the containerized services to read files placed in `./hocr_mount` by the `upload_book.py` script.
    *   `environment:`: Sets environment variables for the container, overriding defaults set in the Dockerfile if necessary.
    *   (Removed `volumes: hocr-data: {}` as the named volume is no longer used).

## 5. Configuring the Nginx Reverse Proxy

Now that the annotation and search services are running in Docker containers, we need a way for the outside world (and the IIIF manifests generated by InvenioRDM) to reach them. We can't just point directly to `http://annotation-service:5002` from a user's browser or the manifest, as those service names only exist *inside* the Docker network.

The solution is to use the existing `frontend` service (which runs Nginx) as a **reverse proxy**.

**What is a Reverse Proxy? (Simple Analogy)**

Imagine a large office building (your Docker environment) with many different departments (the containers like `web-ui`, `annotation-service`, `search-service`). You can't just walk up to any window and talk to the department you want. Instead, there's a main reception desk at the entrance (the Nginx `frontend` container).

You tell the receptionist (Nginx) who you want to talk to (e.g., "I have a request for the `/annotations/` department" or "I need to talk to `/search/`"). The receptionist knows where each department is located inside the building and forwards your request to the correct internal office (`http://annotation-service:5002` or `http://search-service:5001`). When the department replies, the receptionist passes the answer back to you.

To the outside world, it looks like you're only talking to the main reception desk (`https://localhost`), but internally, Nginx is routing the requests based on the URL path.

**Why Use It Here?**

*   **Single Entry Point:** We only need to expose one main web entry point (Nginx on ports 80 and 443) to the host machine.
*   **Simplified URLs:** The IIIF manifests can use clean public URLs like `https://localhost/annotations/...` instead of internal Docker addresses.
*   **HTTPS Termination:** Nginx handles the HTTPS connection (SSL/TLS), so the backend Flask services don't need to worry about certificates (unless desired for internal traffic).
*   **Load Balancing (Future):** If we had multiple instances of a service, Nginx could distribute requests between them.
*   **Security:** Nginx can act as a buffer, potentially blocking malicious requests before they reach the backend services.

### 5.1. How-To: Configure Nginx Location Blocks

The core of the Nginx configuration happens in the `nginx.conf` file. We need to tell Nginx how to handle requests for specific URL paths (like `/annotations/`) and where to forward them. This is done using `location` blocks within the `server { listen 443 ... }` section of the configuration.

**File:** `docker/nginx/nginx.conf`

**Location:** Inside the `server { ... }` block that listens on port 443 (HTTPS). **Crucially, these specific proxy blocks must come *before* the general `location / { ... }` block.**

```nginx
# HTTPS server
server {
    listen 443 ssl http2; # IPv4
    listen [::]:443 ssl http2; # IPv6
    server_name _;
    charset utf-8;
    keepalive_timeout 5;

    # --- NEW: Proxy for Annotation Service ---
    # Match requests starting with /annotations/
    location /annotations/ {
        # Forward the request to the annotation service container
        # The internal address is http://<service_name>:<port>
        # NO trailing slash here, because the backend Flask app expects
        # the full path starting with /annotations/
        proxy_pass http://annotation-service:5002;

        # Standard headers to pass info about the original request
        proxy_set_header Host $host; # Original host requested by client
        proxy_set_header X-Real-IP $remote_addr; # Original client IP
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; # List of IPs if multiple proxies
        proxy_set_header X-Forwarded-Proto $scheme; # http or https
    }

    # --- NEW: Proxy for Search & Autocomplete Service ---
    # Match requests starting with /search/ OR /autocomplete/ using REGEX
    # The '~' means case-sensitive regex match
    # The '^' means "starts with"
    # The '(search|autocomplete)' captures either word
    location ~ ^/(search|autocomplete)/ {
        # Forward to the search service container
        # NO trailing slash here, because the backend Flask app expects
        # the full path starting with /search/ or /autocomplete/
        proxy_pass http://search-service:5001;

        # Standard proxy headers
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # -- Existing InvenioRDM Location Blocks --
    # IMPORTANT: These general blocks MUST come AFTER the specific proxy blocks above

    ## UI server (Handles everything else, including '/api/' requests not matched above)
    location / {
        uwsgi_pass ui_server; # Forwards to the main InvenioRDM app (web-ui)
        include uwsgi_params;
        # ... other uwsgi settings ...
    }
    ## Most API (This might be redundant now if '/' handles it, but kept for compatibility)
    location /api {
        uwsgi_pass ui_server;
        include uwsgi_params;
        # ... other uwsgi settings ...
    }
    ## API files (Specific handling for large file uploads)
    location ~ /api/records/.+/draft/files/.+/content {
        gzip off;
        uwsgi_pass ui_server;
        include uwsgi_params;
        # ... other uwsgi settings ...
    }

    # Static content served directly by Nginx
    location /static {
        alias /opt/invenio/var/instance/static;
        autoindex off;
    }
    # Robots.txt file is served by nginx.
    location /robots.txt {
        alias /opt/invenio/var/instance/static/robots.txt;
        autoindex off;
    }
} # End of HTTPS server block
```

**Key Nginx Concepts Used:**

*   `location <path>`: Matches requests starting with a specific prefix.
*   `location ~ <regex>`: Matches requests based on a case-sensitive regular expression.
*   `proxy_pass <url>`: Forwards the matched request to the specified upstream URL.
    *   **Trailing Slash Importance:**
        *   `proxy_pass http://backend;` (No slash): Appends the *full original request URI* to the backend URL. E.g., `/search/book1` -> `http://backend/search/book1`.
        *   `proxy_pass http://backend/;` (With slash): Appends only the part of the URI *after* the matched location prefix. E.g., `location /search/` + `proxy_pass http://backend/;` + request `/search/book1` -> `http://backend/book1`. We need the **no-slash** version here because our backend Flask apps expect the full `/annotations/...` or `/search/...` path.
*   `proxy_set_header`: Adds or modifies headers sent to the backend service, providing context about the original request.
*   **Order Matters:** Nginx checks location blocks in order. More specific blocks (like `/annotations/`) should generally come *before* more general blocks (like `/`) to ensure they are matched correctly.

## 6. Troubleshooting Proxy Issues: A Developer's Journey

Setting up the reverse proxy wasn't straightforward. Here's a breakdown of the problems encountered and how they were solved. This is a common experience in development!

### Problem 1: 404 Not Found (From Nginx/InvenioRDM)

*   **Symptom:** Running `curl -k https://localhost/annotations/...` returned the standard InvenioRDM "Page not found" HTML page (a 404 error), not a response from the annotation service.
*   **Cause 1: Nginx Config Not Loaded:** Initially, the edits made to the local `docker/nginx/nginx.conf` file were not being used by the running `frontend` container. This was because the `frontend` service definition in `docker-services.yml` was **missing a `volumes` section** to mount the local config file into the container. Nginx was using the default config baked into its Docker image.
    *   **Solution 1a:** Add the volume mount to the `frontend` service definition in `docker-services.yml`:
        ```yaml
          frontend:
            # ... build, image, restart ...
            ports: # Ensure ports are defined
              - "80"
              - "443"
            volumes: # <-- ADD THIS
              - ./docker/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
        ```
    *   **Solution 1b:** Ensure Docker Compose knows about this `frontend` definition. The most reliable way was to copy the *full* service definition (including `build`, `image`, `restart`, `ports`, `volumes`) into the main `docker-compose.yml` file, removing the need for `extends` for this service.
        ```yaml
        # docker-compose.yml
        services:
          frontend: # <-- Full definition here
            build: ./docker/nginx/
            image: turath-inveniordm-frontend
            restart: "unless-stopped"
            ports:
              - "80:80" # Map explicitly
              - "443:443" # Map explicitly
            volumes:
              - ./docker/nginx/nginx.conf:/etc/nginx/nginx.conf:ro
          # ... other services using extends ...
        ```
    *   **Solution 1c:** After modifying the Docker Compose file(s), **recreate the container** for the changes to take effect:
        ```bash
        docker compose up -d --force-recreate frontend
        ```
*   **Cause 2: Incorrect Location Block Order:** Even with the correct config file mounted, the 404s persisted. Debugging showed that the new `location /annotations/ { ... }` and `location ~ ^/(search|autocomplete)/ { ... }` blocks were placed *after* the general `location / { ... uwsgi_pass ui_server; ... }` block in `nginx.conf`. Because `/annotations/` also matches `/`, the general block was catching the request first and sending it to the main InvenioRDM application (which doesn't have these routes), resulting in a 404.
    *   **Solution:** Move the specific proxy location blocks (`/annotations/` and `~ ^/(search|autocomplete)/`) **before** the general `location /` block in the `server { listen 443 ... }` section of `nginx.conf`. (See the correct order in section 5.1). After editing `nginx.conf`, reload Nginx: `docker exec turath-inveniordm-frontend-1 nginx -s reload` (using the actual container name).
*   **Cause 3: Incorrect `proxy_pass` Trailing Slash:** The `annotation-service` Flask app expects the full path `/annotations/<book>/<page>/line`. Initially, the Nginx `proxy_pass` directive had a trailing slash: `proxy_pass http://annotation-service:5002/;`. This caused Nginx to *remove* the `/annotations/` prefix before sending the request, resulting in the backend getting `/history00872/p001/line`, which didn't match its route.
    *   **Solution:** Remove the trailing slash from the `proxy_pass` directive for the `/annotations/` location: `proxy_pass http://annotation-service:5002;`. Reload Nginx after the change. (The `/search` and `/autocomplete` blocks correctly had no trailing slash from the start, matching their backend routes.)

### Problem 2: Connection Refused

*   **Symptom:** Running `curl -k https://localhost/annotations/...` resulted in `curl: (7) Failed to connect to localhost port 443: Connection refused`.
*   **Cause:** Docker Compose was not mapping the container's port 443 to the host's port 443. This happened because the `ports` definition was missing or being ignored in the effective `frontend` service configuration due to issues with `extends` and overriding between `docker-compose.yml` and `docker-services.yml`. Checking `docker compose ps frontend` showed the port mapping was something like `0.0.0.0:53061->443/tcp` (a random host port). Checking `sudo lsof -i :443` confirmed nothing was listening on the host's port 443.
    *   **Solution:** Ensure the `frontend` service definition being used by `docker compose up` includes the correct, non-conflicting port mapping. The most robust solution was to define the *entire* service explicitly in the main `docker-compose.yml` file, including:
        ```yaml
        ports:
          - "80:80"
          - "443:443"
        ```
        Then, recreate the container: `docker compose up -d --force-recreate frontend`. Verify the correct mapping using `docker compose ps frontend`.

### Problem 3: `docker compose logs/exec frontend` fails with "no such service"

*   **Symptom:** Commands like `docker compose logs frontend` or `docker compose exec frontend ...` failed, even though `docker compose ps` showed a running container named `turath-inveniordm-frontend-1` based on the `frontend` service.
*   **Cause:** Likely a quirk in how the specific Docker Compose version handles service discovery for commands when the service is defined using `extends` from another file (like `docker-services.yml`). Explicitly adding `frontend: extends: ...` to the main `docker-compose.yml` seemed necessary for the `up` command but didn't always fix `logs` or `exec`.
    *   **Solution/Workaround:** Target the container directly using its specific name obtained from `docker compose ps`:
        ```bash
        # Instead of: docker compose exec frontend nginx -s reload
        docker exec turath-inveniordm-frontend-1 nginx -s reload

        # Instead of: docker compose logs frontend
        docker logs turath-inveniordm-frontend-1
        ```

## 7. Useful Debugging Commands

When troubleshooting container and proxy issues, these commands are invaluable:

*   **Check Service/Container Status:** Shows running containers, their names, status, and port mappings. Essential for seeing if a container is running and if ports are mapped correctly.
    ```bash
    docker compose ps
    docker compose ps <service_name> # e.g., docker compose ps frontend
    ```
*   **View Container Logs:** Shows the standard output and errors from the process running inside the container. Check Nginx logs for configuration errors or backend service logs for application errors.
    ```bash
    docker compose logs <service_name> # Might fail if service name resolution issue
    docker logs <container_name> # More reliable, get name from 'docker compose ps'
    docker logs <container_name> | tail -n 50 # Show last 50 lines
    ```
*   **Execute Command in Container:** Run a command inside a running container. Useful for reloading Nginx, checking file contents inside the container, etc.
    ```bash
    docker compose exec <service_name> <command> # Might fail
    docker exec <container_name> <command> # More reliable
    # Example: Reload Nginx config
    docker exec turath-inveniordm-frontend-1 nginx -s reload
    # Example: Check Nginx config syntax inside container
    docker exec turath-inveniordm-frontend-1 nginx -t
    # Example: View mounted config inside container
    docker exec turath-inveniordm-frontend-1 cat /etc/nginx/nginx.conf
    ```
*   **Test URLs (from Host):** Use `curl` to make requests to your service endpoints as an external client would.
    ```bash
    # Test HTTPS endpoint on localhost, ignore self-signed cert errors (-k)
    curl -k https://localhost/annotations/history00872/p001/line
    ```

## 8. Version Control (Git)

During the development process, changes were tracked using Git.

*   **Check Status:** See which files have been modified.
    ```bash
    git status
    ```
*   **Stage Changes:** Add modified files to the next commit.
    ```bash
    git add <file1> <file2> # Stage specific files
    git add . # Stage all changes in the current directory and subdirectories
    ```
*   **Commit Changes:** Save the staged changes with a descriptive message.
    ```bash
    git commit -m "feat: Describe the change concisely"
    ```
*   **Push Changes:** Upload local commits to a remote repository (e.g., GitHub).
    ```bash
    # Push current branch to the 'turath' remote, setting upstream tracking (usually only needed first time)
    git push -u turath feature/containerize-services
    # Push subsequent commits on the same branch
    git push turath
    ```
